# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут устанавливать целевую температуру для конкретных комнат или всего дома.
- Система поддерживает автоматическое включение и выключение отопительных приборов (модулей) для достижения заданных параметров.
- Для подключения датчиков нужно вызывать специалиста.

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в реальном времени через интерфейс.
- Система поддерживает сбор данных с датчиков по расписанию.
- Система хранит историю изменений температуры (телеметрию) для последующего анализа.

### 2. Анализ архитектуры монолитного приложения

- Язык программирования: Go
- База данных: Реляционная БД (PostgreSQL), используемая для хранения всех сущностей (устройства, модули, телеметрия).
- Взаимодействие: Все компоненты системы (логика отопления, работа с датчиками, API для пользователя) находятся в одном процессе и используют общую базу данных. Взаимодействие с датчиками происходит синхронно по запросу сервер

### 3. Определение доменов и границы контекстов

- Управление устройствами (Device service): Регистрация и инвентаризация датчиков и отопительных модулей.
  - Регистрация новых датчиков и отопительных модулей, контроль системы отопления.
- Управление пользователями (User service): Регистрация и аутентификация пользователей в системе.
  - Регистрация, аутентификация (JWT), управление профилями и правами доступа к домам.
- Мониторинг (Monitoring service): Сбор, хранение и отображение исторических данных о температуре.
  - Прием данных от датчиков, хранение данных, предоставление графиков.

### **4. Проблемы монолитного решения**

- Невозможно масштабировать только модуль сбора телеметрии (который нагружен сильнее всего) отдельно от логики управления.
- Ошибка в коде формирования отчетов может привести к падению всей системы, включая управление отоплением.
- Любое мелкое изменение требует пересборки и перезапуска всего приложения.
- При росте количества датчиков синхронный опрос в монолите может стать узким местом.

### 1. Тип API

Для взаимодействия между микросервисами и фронтендом будет использоваться REST API (HTTP/JSON), так как это стандарт индустрии с отличной поддержкой инструментов (например, Swagger). Для сбора телеметрии в будущем оправдано использование gRPC или брокера сообщений (RabbitMQ) для повышения пропускной способности.

# Задание 5. Работа с docker и docker-compose

1.
```
  temperature-api:
    build:
      context: ./temperature-api
    container_name: temperature-api
    ports:
      - "8081:8081"
    networks:
      - smarthome-network
    restart: unless-stopped
    depends_on:
      postgres:
        condition: service_healthy
```

2. 
```
  postgres:
    image: postgres:16-alpine
    container_name: smarthome-postgres
    environment:
      - POSTGRES_DB=smarthome
      - POSTGRES_USER=postgres
      - POSTGRES_PASSWORD=postgres
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
      - ./smart_home/init.sql:/docker-entrypoint-initdb.d/init.sql
    networks:
      - smarthome-network
    healthcheck:
      test: [ "CMD-SHELL", "pg_isready -U postgres -d smarthome" ]
      interval: 5s
      timeout: 5s
      retries: 5
```
