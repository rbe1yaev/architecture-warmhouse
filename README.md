### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут включать и выключать отопление;
- Система поддерживает только ручное управоление
- Нельзя самостоятельно подключить новую систему отопления, требуется обязательный выезд мастера

**Мониторинг температуры:**

- Пользователи могут проверять температуру
- Система поддерживает получение данных от подключенных датчиков
- Нельзя самостоятельно подключить датчик

### 2. Анализ архитектуры монолитного приложения

- Язык программирования Go
- СУБД PostgreSQL
- Всё синхронно. Никаких асинхронных вызовов, микросервисов и реактивного взаимодействия в системе нет. 
- Самостоятельно подключить свой датчик к системе пользователь не может.

### **4. Проблемы монолитного решения**

- Низкая отказоустойчивость (при падении монолитного приложения становится недоступна вся система);
- Высокий риск изменений (любое обновление требует полного ретестирования всего функционала из-за сильной связанности компонентов);
- Сложность масштабирования (невозможно масштабировать отдельные компоненты независимо);
- Длительные деплои (процесс развёртывания обновлений занимает много времени и сопряжён с простоями, особенно при выполнении миграций базы данных)

Если вы считаете, что текущее решение не вызывает проблем, аргументируйте свою позицию.
- Когда важно быстро выпускать продукт, а сложность микросервисов избыточна;
- Отсутствие средств на реализацию микросервисов;
- Команда разработки мала и эффективно работает с монолитом.

# Задание 4. Создание и документирование API

### 1. Тип API
В рамках микросервисной архитектуры используются оба типа взаимодействия: синхронное и асинхронное.

В микросервисной архитектуре используются оба типа API. Для взаимодействия между микросервисами gateway, auth, device-manager, device, telemetry используется REST API и синхронные вызовы.
Синхронное взаимодействие (REST API): Применяется для связи между микросервисами gateway, auth, device-manager, device и telemetry.
Асинхронное взаимодействие (события): Используется между микросервисами telemetry и pusher для доставки обновлений данных. 
Pusher, в свою очередь, отвечает за рассылку уведомлений пользователям через постоянное WebSocket-подключение.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps. В docker-compose.yml добавлен temperature-api и запуск postgres db с созданием таблицы sensors. Исправлен init.sql

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Задание 6. Разработка MVP
Внедрена микросервисная архитектура в соответствии с диаграммами из заданий 3 и 4.
Приложения размещены в модуле warmhouse, каждый микросервис имеет Dockerfile.
Реализован файл docker-compose для запуска всех микросервисов, их баз данных и Kafka.
План интеграции с существующим монолитным приложением:
1. Микросервис ms_device: Реализует эндпоинты, совместимые с эндпоинтами монолита (sensors.go).
На начальном этапе для переноса данных ms_device и smart_home могут использовать общую базу данных.
Создание новых сенсоров будет записываться в базу ms_device.
2. Микросервис ms_gateway: В нём реализуются легаси-роутеры монолита. Трафик постепенно переключается с монолита на ms_gateway.
3. Фронтенд: Производится его переключение на новые эндпоинты микросервисов.
4. После полного перехода монолитное приложение становится ненужным и удаляется.
