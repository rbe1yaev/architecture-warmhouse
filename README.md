### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут управлять отоплением в доме через приложение
- Система поддерживает только один тип реле, новые устройства не поддерживаются
- управление системой от сервера к реле

**Мониторинг температуры:**

- Пользователи могут проверять температуру в доме
- Система поддерживает только один тип датчика, новые устройства не поддерживаются
- получение информации о температуре от сервера к датчику

**Подключение новых устройств:**

- Самостоятельно подключить свой датчик к системе пользователь не может, для подключения и настройки требуется выезд
  специалистов компании

### 2. Анализ архитектуры монолитного приложения

- база данных - Postgres
- язык решения GO
- все запросы являются синхронными, как следствие каждый запрос блокирует код, до момента выполнения
- все взаимодействие между компонентами происходит от сервера к компонентам, пользователь взаимодействует с сервером
  через приложение

### 3. Определение доменов и границы контекстов

#### Основной домен компании

__Описание__: отвечает за управление отоплением в доме.

#### Поддомен 1. взаимодействие домом

- __контекст__: отправка команд на реле упраления;
- __контекст__: получение данных о температуре путем запроса;
- __контекст__: сохранение данных о температуре в базе;

#### Поддомен 2. взаимодействие с устройствами

- __контекст__: CRUD api для устройств;
- __контекст__: получение данных о температуре путем запроса;
- __контекст__: сохранение данных о температуре в базе;

### **4. Проблемы монолитного решения**

- Сильно связанные компоненты, каждое изменение вносится во все решение целиком, что затрудняет деплой, повышает риск
  ошибки
- язык Go хорош для скорости, но не так гибок для например валидаций и прочего
- (проблема конкретно этого решения) - полная синхронность, с ростом числа устройств и усложнения логики управления
  устройствами, монолит
  может упереться в скорость опроса устройств, то есть миллион устройств с учетом синхронности запросов он будет
  опрашивать пол дня
  добавление асинхронных запросов, а так же высокопроизводительных брокеров сообщений (Kafka) сможет распределить
  нагрузку
- к слову о брокерах, такое решение будет хоть как-то существовать до 1000 устройств, далее начнутся проблемы с
  производительностью
- в текущем решении сервер опрашивает устройства, так что приходится хранить все адреса устройств
- если вдруг появится новое устройство, придется вносить изменения в весь код, можно проглядеть место, где изменения
  порушат какую-то модель

# Задание 4. Создание и документирование API

### 1. Тип API

REST API Синхронные запросы между сервисами и клиентами
AsyncAPI / Event-driven Асинхронный обмен событиями между сервисами

Команда небольшая — 5 разработчиков.
REST проще в разработке, отладке и тестировании.
Swagger UI из коробки — удобно для команды поддержки.
gRPC не даст большого прироста при небольших нагрузках

Взаимодействие пользователя с системой - синхронное, там нужен ответ сразу

Телеметрия — это постоянный поток данных от устройств.
Ждать ответа на каждое показание нецелесообразно.
Уведомления не должны блокировать основной поток.
Один и тот же event могут получить несколько сервисов
без прямой зависимости между ними.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе
   /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска
   postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
